**Status:** proposed, awaiting approval. Nothing in `src/` or `tests/` has been touched yet.

re-verified against the files before being accepted. What changed:

4. The `ClientId` guard needs no new endpoint code at all if it throws the right exception type, and the

## 0. Two decisions to make before anything starts

Both reshape Steps 6–8 and §6b.5. Neither is mine to make.

### 0.1 Hard cut, or additive rc.8 with `[Obsolete]`?

Revisions 1 and 2 assumed a hard cut: rename and delete in one release, with the consumer following in lockstep.
Every awkward part of this plan descends from that unexamined assumption — the cross-repo gate order, the
deadlock in §6b.5, the size of Step 7, and the "confirm no other consumer exists" precondition on a package
that is public on nuget.org.

The alternative: rc.8 **adds** `ExportRequest`, `ExportArchive` and `TriggerExportAsync`, marks the `Dsfinvk*`
types and the three trigger methods `[Obsolete("Use ExportRequest / TriggerExportAsync; removed in rc.9.")]`,
and deletes outright only the segment subsystem — which is genuinely unreachable and genuinely unused.

| | Hard cut | Additive |
|---|---|---|
| Vectis compiles on rc.8 unchanged | no | **yes** |
| §6b.5 deadlock | must be worked around | dissolves |
| Consumer migration driven by | a 67-line grep across 9 files | the compiler, at its own pace |
| Misleading names live on | no | one more RC, with a warning pointing at the replacement |
| Release is an all-or-nothing two-repo transaction | yes | no |

The project's own precedent favours additive: rc.7's release notes end *"source-compatible for anyone who
catches `FiskalyException`; only code that catches `InvalidOperationException` specifically around a download
needs to change."* rc.8 as drafted removes eleven public types, three public methods and a namespace at once.

**Recommendation: additive.** The remainder of this plan is written for the hard cut and notes where the
additive shape differs; if additive is chosen, Steps 1–4 stay and Steps 6–8 and §6b.5 simplify considerably.

### 0.2 `Tse*` or `Export*`?

Revision 2 recommended `TseExportArchive` / `TseExportRequest`, and that recommendation was approved. A review
then raised an argument that was not on the table when it was approved, and it is a strong one:

**`TssId` is the central noun of this namespace — it appears in nine export signatures.** The result would be

```csharp
Task<ExportJob> TriggerExportAsync(TssId tssId, ExportId exportId, TseExportRequest request, …)
```

`Tss` and `Tse` in one signature, one letter apart, one of them fiskaly's word and the other the BSI's. That
is a worse ambiguity than the one being fixed.

The forward-looking argument for the `Tse` prefix also does not hold. A future DSFinV-K API client belongs in
`SYT.Fiskaly.Dsfinvk.Exports` — the SDK already partitions by product, and `SYT.Fiskaly.Dsfinvk.Enums` exists.
Two `ExportArchive` types in two product namespaces is the ordinary case namespaces exist to solve.

The alternative needs no justification at all: the file is already called `Models/ExportRequest.cs` and the
base class this plan keeps is already `ExportRequestBase`, so `ExportRequest : ExportRequestBase` reads as
what it is. If `ExportArchive` seems thin, `ExportFile` is fiskaly's own noun (`retrieveExportFile`,
*"Retrieve the TAR file generated by an export operation"*).

The counter-argument for `Tse*` remains real: the archive is TSE log data and nothing else, and a name that
says so kills the misreading that started this ticket. But that is what an XML doc comment carries. Naming
carries identity; docs carry content.

**Revised recommendation: `ExportArchive` / `ExportRequest`.** This reverses revision 2. The tables below
still read `Tse*`; substitute if this is accepted.

## 1. The defect

The SDK exposes fiskaly's SIGN DE export endpoints through types named `Dsfinvk*`:

| Type | Namespace |
|---|---|
| `DsfinvkArchive` | `SYT.Fiskaly.SignDE.Exports.Dsfinvk` |
| `DsfinvkFullExportRequest` | `SYT.Fiskaly.SignDE.Exports.Models` |
| `DsfinvkClientExportRequest` | `SYT.Fiskaly.SignDE.Exports.Models` |
| `DsfinvkLogExportRequest` | `SYT.Fiskaly.SignDE.Exports.Models` |
| `DsfinvkExportRequestBase` | `SYT.Fiskaly.SignDE.Exports.Models` |
| `DsfinvkSegment`, `DsfinvkSegmentType`, `IDsfinvkVersionStrategy`, `DsfinvkV2SegmentStrategy`, `UnknownDsfinvkSegment`, `MasterDataSegment`, `TransactionSegment`, `CashPointClosingSegment` | `SYT.Fiskaly.SignDE.Exports.Dsfinvk` |

Those endpoints do not produce DSFinV-K data. The naming misleads, and it has already cost a consumer real
time: someone reading `DsfinvkArchive` reasonably concludes fiskaly hands us the DSFinV-K CSV bundle and goes
looking for an API that does not exist on this host.

### 1.1 Evidence from fiskaly's own specs

Both specs ship in this repository under `src/SYT.Fiskaly/Documentation/official-documentation/`.

**`fiskaly-openapi-sign-de-spec-v2.1.35.json`** — the API these types wrap.

- Paths: `/api/v2/tss/{tss_id}/export`, `/api/v2/tss/{tss_id}/export/{export_id}`,
  `…/file`, `…/metadata`, `/api/v2/export`.
- OpenAPI tag on every export operation: `"Data Exports"`.
- operationIds: `listExports`, `triggerExport`, `retrieveExport`, `cancelExport`, `retrieveExportFile`,
  `retrieveExportMetadata`, `updateExportMetadata`, `listAllExports`.
- Components: `ExportResponse` (`_type: "EXPORT"`), `ExportState`, `ExportException`, `ExportId`,
  `ExportListResponse`, `TriggerExportsQuerystring`.
- What the archive holds, verbatim from `info.description` under the heading `## Export`:

  > The export resource holds the state of the asynchronous generation of the export TAR file.
  > The export TAR file contains the SMAERS initialization information, the signed log messages, and the
  > certificates to verify them.

- `retrieveExportFile` summary, verbatim: `Retrieve the TAR file generated by an export operation`.
- Word frequencies over the whole spec: `export` 212, `TAR file` 15, `log message` 28,
  **`TSE export` 0, `log export` 0**.
- `DSFinV-K` appears 29 times — **zero of them inside any `/export` path object or any `Export*` component**.
  Every hit is about transaction payload field mappings (`BON_TYP`, `UST_SATZ`, `ZAHLART_TYP`, `MENGE`,
  `ARTIKELTEXT`) or the 70-character limit on `ClientSerialNumber`.

**`fiskaly-openapi-dsfinv-k-spec-v1.27.4.json`** — a *different* API.

- `info.title`: `fiskaly DSFinV-K API`; base URL `https://dsfinvk.fiskaly.com/api/v1` — a different host.
- Resources: `/cash_point_closings`, `/cash_registers`, `/vat_definitions`, `/purchaser_agencies`, `/exports`.
- `Exports` tag description, verbatim:

  > This export will provide a set of csv files according to DSFinV-K standard to comply with financial
  > regulations.

- It names SIGN DE throughout (`SIGN DE TSS`, `SignDe*` schemas) and links to it by UUID (`tss_id`,
  `client_id`, `tx_id`) — but it never references the SIGN DE **export** endpoint, resource, or artifact.
  The narrow claim is the load-bearing one; revision 1 overstated it as "only by UUID".

**`fiskaly-kassensichv-v2.postman_collection.json`** — fiskaly's own human-facing labels for these very calls:
`"Trigger Export"`, `"Retrieve Export"`, `"Retrieve the export file"`, `"List Exports of a TSS"`. Never
"DSFinV-K export". The strings `tar`, `zip`, `csv` appear zero times in that collection.

### 1.2 Evidence from a real archive

`tests/SYT.Fiskaly.UnitTests/TestData/dsfinvk-sample.tar` — 138 entries produced by a live TSS:

| Kind | Count | Example |
|---|---|---|
| `.log` (ASN.1 DER records) | 134 | `Unixt_1758884351_Sig-7_Log-Aud.log`, `Unixt_…_Sig-N_Log-Tra_No-10_Finish_Client-VECTIS-DEV-KASSE-001.log` |

## 2. A second defect found while investigating

`DsfinvkFullExportRequest` exposes `ClientId` alongside `StartDate`, `EndDate`, and the inherited signature
counter and transaction-number ranges. The spec forbids that combination:

> `client_id` — Only return log messages associated with the given client (**other query parameters will be
> ignored**).

and, in the `triggerExport` description:

> Note: The query parameter `client_id` is not meant to be used in combination with other query parameters.

Setting `ClientId` together with any other filter therefore produces a silently different export than the
caller asked for. Nothing in the SDK rejects it. The three-class split creates the impression of a guard that
does not exist — `DsfinvkClientExportRequest` is client-only, but `DsfinvkFullExportRequest` is not.

### 2.1 The combination is reachable from outside, and the fix must not become a 500

Revision 1 claimed Vectis never produces this combination. That was checked against Vectis's own *hardcoded*
call sites and is wrong for the one that matters: `ToSdkFullExportRequest`
(`src/Pos/Vectis.Api/Endpoints/FiscalizationManagementEndpoints.cs:848-861`) copies **caller-supplied HTTP
input** field by field:

```csharp
private static DsfinvkFullExportRequest ToSdkFullExportRequest(TriggerFullExportRequest request)
{
    return new DsfinvkFullExportRequest
    {
        StartDate = request.StartDate?.ToUniversalTime(),
        EndDate = request.EndDate?.ToUniversalTime(),
        ClientId = request.ClientId.HasValue ? ToClientId(request.ClientId.Value) : null,
        MaximumNumberRecords = …, StartSignatureCounter = …, EndSignatureCounter = …,
        StartTransactionNumber = …, EndTransactionNumber = …
    };
}
```

and `TriggerFullExportRequest` (`src/Pos/Vectis.Contracts/V1/Fiscalization/Requests/TriggerFullExportRequest.cs`)
declares `ClientId`, `StartDate`, `EndDate` and all four counters as independent optional properties with **no
validation anywhere in the endpoint**. Any API client can send the forbidden combination today and receive
fiskaly's client-only behaviour.

Consequence for this plan: once §4.1's guard exists, that same request throws inside `Apply()` and — if it
throws `InvalidOperationException` — escapes as an unhandled **500**.

### 2.2 The 500 is not new, and the fix is one word

Two things revision 2 got wrong about this.

**First, the hazard already exists, three times.** `ExportRequest.cs` throws `InvalidOperationException` today
at lines 46, 52 and 94 — reversed signature-counter range, reversed transaction-number range, and
`EndDate < StartDate`. All three travel the same uncaught path. Any caller can already get a 500 out of
`POST /tss/{tssId}/exports/full`. The new guard *joins* that hazard rather than creating it.

**Second, no endpoint code is needed.** `FiskalyException` is a plain `public class FiskalyException : Exception`,
and the consumer already has the whole chain:

```csharp
// ExportManagementService.cs:92, 126, 192
catch (FiskalyException ex) { return Result<ExportJob>.Failure($"Failed to trigger export: {ex.Message}"); }

// FiscalizationManagementEndpoints.cs:636-638
return result.IsSuccess ? Results.Ok(…) : Results.BadRequest(OperationResultDto.Failure(result.Error));
```

Throw **`FiskalyValidationException : FiskalyException`** and the 400 with a useful message already exists, in
both repositories, with no new endpoint code and no new endpoint test.

This is exactly the pattern rc.7 established — its own release notes say `DownloadExportAsync` was changed to
raise `FiskalyExportNotReadyException` instead of a bare `InvalidOperationException` precisely because the old
type *"sat outside the FiskalyException hierarchy every caller catches… and surfaced as an HTTP 500."*
Revision 2 was about to recreate that bug in the adjacent method.

**Therefore:** convert all four throws — the three existing ones and the new `ClientId` guard — to
`FiskalyValidationException` in the same commit. Keep one integration test asserting the 400; it now costs
nothing. Delete revision 2's "add an endpoint-side 400" work item from Step 7.

One thing this does **not** cover: `ExportLimit.From` throws `ArgumentOutOfRangeException` for values outside
1..1 000 000, and `ToSdkFullExportRequest` runs *outside* the service's try block, so
`maximumNumberRecords: 0` is an unhandled 500 today and stays one. That is a separate ticket, not this one.

## 3. The segment subsystem is unreachable, not merely misnamed

`DsfinvkV2SegmentStrategy.CreateSegment` classifies archive entries by substring on the file name
(`src/SYT.Fiskaly/SignDE/Exports/Dsfinvk/DsfinvkV2SegmentStrategy.cs:127-149`):

```csharp
if (lowered.Contains("master"))       return new MasterDataSegment(…);
if (lowered.Contains("transaction") || lowered.Contains("receipt") || lowered.Contains("tx"))
                                      return new TransactionSegment(…);
if (lowered.Contains("closing") || lowered.Contains("cashpoint") || lowered.Contains("cash_point"))
                                      return new CashPointClosingSegment(…);
return new UnknownDsfinvkSegment(…);
```

Matches across all 138 entries of the sample archive: `master` 0, `transaction` 0, `receipt` 0, `tx` 0,
`closing` 0, `cashpoint` 0, `cash_point` 0. **Everything classifies as `UnknownDsfinvkSegment`.**
`MasterDataSegment`, `TransactionSegment` and `CashPointClosingSegment` are unreachable for any real SIGN DE
export. The repository's own test says so — `DsfinvkV2SegmentStrategyTests.cs:105-106`:

```csharp
// The dsfinvk-sample.tar contains log files that don't match master/transaction/closing patterns
// So they should be categorized as Unknown
```

There is no CSV parsing, no header validation, no DSFinV-K file-name table. `Version => "2.x"` is a literal that no production
code reads — though `DsfinvkArchiveTests.cs:99` asserts it, so it is not entirely unreferenced.

Related latent bug: `DsfinvkSegment.OpenJsonDocument()` (`DsfinvkSegment.cs:27`) calls `JsonDocument.Parse` on
the entry bytes. Every entry in a real export is ASN.1 DER or a certificate, so that method always throws.

The only consumer (Vectis) reads `RawContent` and nothing else — no `.Segments`, no `.OfType<>()`, no
`.OpenRawStream()`, no `.OpenJsonDocument()` anywhere.

**Decision: delete the subsystem rather than rename it.** It models a format this endpoint never returns.

### 3.1 The "eager corrupt-archive check" does not exist — measured

Revision 2 claimed that deleting the strategy removes a real integrity check, because `DownloadExportAsync`
runs the bytes through `TarReader` before returning. The mechanism is real
(`ExportClient.cs:129-131` → `DsfinvkArchive.FromStreamAsync:42` → `TarReader`). What it catches is not.

Measured against the repository's own sample archive (144 384 bytes, 138 entries), running the same
`TarReader` loop `ParseTarAsync` uses:

| Input | Result |
|---|---|
| full | OK, 138 entries |
| truncated by 1 byte | OK, 138 entries |
| **truncated to 50 %** | **OK, 70 entries — no throw** |
| first 10 240 bytes | OK, 10 entries |
| 4 096 bytes of garbage | threw `InvalidDataException` |
| 4 096 zero bytes | OK, 0 entries — no throw |

`TarReader` treats a truncated stream as end-of-archive. **Half a journal parses cleanly as a valid archive.**
The check catches only "this is not a tar at all" — and even that is largely redundant, because
`DownloadExportAsync` uses `GetAsync` with the default `ResponseContentRead`, so a transport-truncated body
fails as `HttpRequestException` before any parsing.

The consumer is also less defenceless than revision 2 implied: `TseJournalArchiveProcessor.cs:653-660` refuses
an empty download outright ("Refused rather than archived"), and `MinioFiscalArchiveStore` re-verifies the
stored bytes against SHA-256 before applying the lock (`VerifyStoredBytesBeforeLockingAsync`, covered by
`FiscalArchiveVerifyBeforeLockTests`). What is genuinely unguarded is a **non-empty but partial** journal.

**Consequence:** the risk-register row and open question about preserving this check are withdrawn — there is
nothing worth preserving. If partial-journal detection is wanted, it is new work and it belongs in the
consumer, which is the only party that knows what it asked for: next to the existing `content.Length == 0`
guard, enumerate the archive and refuse if the signature counters in the `Unixt_{time}_Sig-{counter}_…`
filenames do not span `entry.AssignedFromCounter..AssignedToCounter`. A format check in the SDK would pass a
50 %-truncated journal, as measured above. **Raised as separate work, not part of rc.8.**

## 4. Naming decision

Fiskaly's own noun is the bare `export`, because inside SIGN DE there is only one export to name. That
uniqueness does not survive the trip to a consumer that also builds its own DSFinV-K bundle, so copying their
vocabulary literally would import an ambiguity they do not have. The German regulation (BSI TR-03153,
KassenSichV) calls this artifact the *TSE-Export*, and the content genuinely is TSE log data.

`Tse` also survives a plausible future: if this SDK ever gains the separate DSFinV-K API, that product has its
own archive, and a bare `ExportArchive` in two namespaces would collide in every file holding both `using`s.

| Current | New | Note |
|---|---|---|
| `DsfinvkArchive` | `TseExportArchive` | |
| `DsfinvkFullExportRequest` | `TseExportRequest` | absorbs all nine query parameters |
| `DsfinvkLogExportRequest` | *(deleted)* | folded into `TseExportRequest` |
| `DsfinvkClientExportRequest` | *(deleted)* | folded into `TseExportRequest` |
| `DsfinvkExportRequestBase` | *(deleted)* | its properties move onto `TseExportRequest` |
| `ExportRequestBase` | unchanged | correct as-is: query-parameter plumbing |
| namespace `SYT.Fiskaly.SignDE.Exports.Dsfinvk` | *(removed)* | `TseExportArchive` moves to `SYT.Fiskaly.SignDE.Exports` |
| `TestData/dsfinvk-sample.tar` | `TestData/tse-export-sample.tar` | path is a string literal in 7 places; the compiler will not catch it |

**Deleted outright:** `DsfinvkSegment`, `DsfinvkSegmentType`, `IDsfinvkVersionStrategy`,
`DsfinvkV2SegmentStrategy`, `UnknownDsfinvkSegment`, `MasterDataSegment`, `TransactionSegment`,
`CashPointClosingSegment`, the `strategy` parameter on `IExportClient.DownloadExportAsync`, the
`dsfinvkStrategy` primary-constructor parameter on `ExportClient`, and **two** DI sites in
`ServiceCollectionExtensions.cs` — the registration at line 77
(`AddSingleton<IDsfinvkVersionStrategy, DsfinvkV2SegmentStrategy>()`) **and** the factory closure at line 125
(`sp => [sp.GetRequiredService<IDsfinvkVersionStrategy>()]` inside `AddFiskalyScopedClient<IExportClient, …>`).

Test files affected — revision 1 said "~86 unit-test lines", which was wrong by roughly 8x:

| File | Lines | Disposition |
|---|---|---|
| `Dsfinvk/DsfinvkSegmentTests.cs` | 226 | delete wholly |
| `Dsfinvk/DsfinvkV2SegmentStrategyTests.cs` | 226 | delete wholly |

### 4.1 New `TseExportRequest` shape

One class mirroring `TriggerExportsQuerystring` — all nine parameters, all optional:

`ClientId`, `TransactionNumber`, `StartTransactionNumber`, `EndTransactionNumber`, `StartDate`, `EndDate`,
`MaximumNumberRecords`, `StartSignatureCounter`, `EndSignatureCounter`.

**All three existing validations must survive**, not just the date one revision 2 named. `ApplyCommonFilters`
throws today on a reversed signature-counter range (`ExportRequest.cs:46`), a reversed transaction-number range
(`:52`), and `EndDate < StartDate` (`:94`); existing tests assert the first two
(`DsfinvkFullExportRequestTests.cs:113,126`). Dropping any of them is a silent regression.

`Apply()` therefore keeps all three, converts them to `FiskalyValidationException` (§2.2), and **adds** the
`ClientId` exclusivity guard.

**Which properties trigger the guard.** The spec says all other query parameters are ignored, so the guard
fires when `ClientId` is combined with any of the other **eight** — including `MaximumNumberRecords`, which is
a filter in fiskaly's model even though it reads like a cap. Stating this explicitly because it is the one
property where "is this another filter?" is a fair question.

**Keep one compile-time guarantee the collapse would otherwise destroy.** Today `DsfinvkClientExportRequest`
is `sealed`, takes `ClientId` as a required constructor parameter, and exposes nothing else — a client-only
export *cannot* be built wrong. Replacing that with a runtime throw is a downgrade on a path that feeds a
ten-year lock. Four lines restore it:

```csharp
public static TseExportRequest ForClient(ClientId clientId) => new() { ClientId = clientId };
```

Call sites read `TseExportRequest.ForClient(id)`: intent documented, exclusivity unbreakable, still one type
and one method. §6b.1 asserts that `ForClient` sets nothing else.

### 4.2 The three trigger methods collapse too

Not stated in revision 1, and larger than a type rename. `IExportClient` declares **three separately named
methods** — not overloads — all hitting the identical endpoint and differing only in request type
(`src/SYT.Fiskaly/SignDE/Exports/IExportClient.cs:19,28,37`):

```csharp
Task<ExportJob> TriggerFullExportAsync  (TssId, ExportId, DsfinvkFullExportRequest,   CancellationToken = default);
Task<ExportJob> TriggerClientExportAsync(TssId, ExportId, DsfinvkClientExportRequest, CancellationToken = default);
Task<ExportJob> TriggerLogExportAsync   (TssId, ExportId, DsfinvkLogExportRequest,    CancellationToken = default);
```

One request type means one method: **`TriggerExportAsync(TssId, ExportId, TseExportRequest, CancellationToken)`**.

This ripples further than the SDK. Vectis mirrors the same three-way split on its own
`IExportManagementService` (`TriggerFullExportAsync` / `TriggerClientExportAsync` / `TriggerLogExportAsync`),
which endpoints and the journal archiver both consume. Step 7 must collapse that interface as well, or
deliberately keep the three application-level methods as thin wrappers over one SDK call — a decision to make
before starting, not during.

**Explicitly NOT renamed** — these are correctly named and must be left alone:

- `SYT.Fiskaly.Dsfinvk.Enums.BusinessCaseType` — real DSFinV-K `GV_TYP` vocabulary.
- `SYT.Fiskaly.Dsfinvk.Enums.DsfinvkPaymentType` — real DSFinV-K `ZAHLART_TYP`, cites *DSFinV-K v2.4, Anhang D*.
- `DecimalToStringJsonConverterTests` method names mentioning DSFinV-K — the 5-decimal money rule.
- The export-job plumbing: `IExportClient`, `ExportClient`, `ExportJob`, `ExportState`, `ExportType`,
  `ExportExceptionCode`, `ExportSortField`, `ExportId`, `ExportLimit`, `ExportSortOption`, `SignatureCounter`,
  `TransactionSequenceNumber`, `ListExportsQueryParameters`, `ListExportsResponse`, `ExportJobExtensions`,
  `ExportExceptionInfo`, `ExportExceptionMetadata`, `FiskalyExportNotReadyException`. These match fiskaly's
  vocabulary already and carry no ambiguity.

## 6b. Verification — what must be proven, and by which kind of test

A rename that compiles is not a rename that works. Three layers are required, and none of them substitutes for
another: the compiler proves the names line up, unit tests prove the query string is still built correctly,
integration tests prove fiskaly still accepts it, and e2e proves the till still closes a shift.

### 6b.1 Unit — SDK (`SYT.Fiskaly.UnitTests`, no credentials, runs in CI)

Existing coverage to keep green after the collapse — currently spread across
`Models/DsfinvkFullExportRequestTests.cs`, `Models/DsfinvkLogExportRequestTests.cs`,
`Models/DsfinvkClientExportRequestTests.cs`. These merge into one `TseExportRequestTests`.

New or ported assertions, each of which would catch a real mistake:

| Assertion | Catches |
|---|---|
| Each of the nine properties emits its exact fiskaly query key: `client_id`, `transaction_number`, `start_transaction_number`, `end_transaction_number`, `start_date`, `end_date`, `maximum_number_records`, `start_signature_counter`, `end_signature_counter` | a typo'd key silently drops a filter and exports the wrong range |
| `StartDate` / `EndDate` serialize as **Unix seconds**, not ISO-8601 | the current code calls `ToUnixTimeSeconds()`; a rewrite that "tidies" this breaks the wire format with no compiler complaint |
| Unset properties emit **no** key at all | an empty-string filter is not the same as an absent one |
| `EndDate < StartDate` throws | behaviour that exists today and must survive |
| **`ClientId` set together with any other filter throws** | the §2 defect — the whole point of the collapse |
| `ClientId` alone succeeds | the exclusivity check must not over-fire |
| `TseExportArchive.FromStreamAsync` preserves bytes exactly (`RawContent` equals the input stream byte-for-byte, including for a non-seekable stream) | the archive is placed under a ten-year object lock; a single mangled byte is unrecoverable |
| `DownloadExportAsync` no longer takes a strategy and never parses | proves the deletion actually removed the work, not just the parameter |

Deleted with the subsystem: `DsfinvkArchiveTests.cs` (the segment-related cases), `DsfinvkSegmentTests.cs`,
`DsfinvkV2SegmentStrategyTests.cs`. **Do not delete the whole of `DsfinvkArchiveTests.cs` blindly** — the
RawContent / stream-handling cases in it are the ones that must survive as `TseExportArchiveTests`.

### 6b.4 E2E — Vectis (Playwright)

**Gap found while writing this plan: there is no e2e coverage of the path this change touches.**
`tests/e2e/tests/fiscal-smoke.spec.ts` has two cases — `payment -> signature -> receipt` and
`connection dropped -> worker recovers -> reprint is signed`. Both stop at the receipt. Nothing exercises the

Required before rc.8 is considered verified:

### 6b.5 Order of gates — revision 2's version was a deadlock

Revision 2 ordered them:

```
SDK unit → SDK integration → Vectis bumped to rc.8 → Vectis unit + integration → Vectis e2e
```

and then said *"no version is published until every gate above is green."* Gates 3–5 require a **published**
rc.8. Vectis's `nuget.config` is `<clear />` plus nuget.org only — an unpublished version is unresolvable — and
`release.yml` pushes without `--skip-duplicate`, so a version burned on testing can never be re-pushed. The
plan forbade publishing until after gates that could not run without publishing.

**This only bites under the hard cut.** If §0.1 chooses additive, Vectis compiles against rc.8 unchanged, so
its gates are an ordinary post-publish bump and the ordering below is unnecessary.

For the hard cut, the mechanism already exists and is established practice here: `artifacts/local-feed/`
(gitignored, currently holding `SYT.Fiskaly.1.0.0-rc.4.nupkg`).

```
SDK unit
  → SDK integration (live TEST)
  → pack rc.8 into artifacts/local-feed, point Vectis at it via a temporary source
  → Vectis unit + integration + e2e
  → publish rc.8
  → flip Vectis to PackageReference 1.0.0-rc.8, re-run its build and tests
  → merge
```

Two cautions: the temporary feed source must **not** reach the Vectis PR (it is a local-only edit to
`nuget.config`), and the locally packed nupkg must be byte-identical in content to what CI later publishes —
CI builds from its own checkout, so treat the local pack as a test vehicle, never as the release artifact.
